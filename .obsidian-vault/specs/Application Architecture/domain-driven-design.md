## Definition

Domain-Driven Design (DDD) is an approach to software development that centers the software on a core domain and domain logic, using a ubiquitous language and bounded contexts.

## Problem Addressed

Without Domain-Driven Design:
- Domain is unclear
- Logic is scattered
- Language is inconsistent
- Models are weak

## Scope of Boundaries

Domain-Driven Design applies to:
- Domain modeling
- Bounded contexts
- Strategic design
- Tactical design

Domain-Driven Design does not apply to:
- Backend code
- Database design
- Infrastructure
- Testing

## When to Apply

- Building complex apps
- Needing domain clarity
- Wanting ubiquitous language
- Modeling domains

## Tradeoffs and When to Avoid

- **Complexity**: Domain-Driven Design adds complexity
- **Not for simple apps**: Simple apps may not need Domain-Driven Design
- **Not for internal**: Internal apps may not need Domain-Driven Design
- **Not for all**: Not all apps need Domain-Driven Design

## Implementation Guidance

1. **Explore domain**: Explore domain with experts
2. **Define ubiquitous language**: Define ubiquitous language
3. **Define bounded contexts**: Define bounded contexts
4. **Model domain**: Model domain entities
5. **Test**: Test domain model
